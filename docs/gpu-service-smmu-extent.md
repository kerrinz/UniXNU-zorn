# Declared extent before direct SMMU diagnostic loads

Exact Service source checked a published window count and nonnull virtual pointer,then performed five direct32-bit diagnostic loads up to offset0x48 without checking the declared window byte length. Board::parseReg rejects zero/overflowing windows but permits nonzero lengths below0x4c. SmmuService publishes those parsed bytes via windowBytes and does not promise this diagnostic minimum. Mapping existence or a rounded mapping allocation is not a substitute for the declared extent. This is a missing source range guard;no mapped-window failure or K80 short-window condition was observed.

An independent UNAPPLIED candidate uses an if-initializer over the single existing windowBytes result and gates the original block on at least0x4c bytes. That minimum is exactly the largest existing load offset plus its4-byte width,not a guessed K80 aperture or mapping authority. The same getter count,raw loads,offsets,order,log formats,bringup bodies and selectors remain. No new return,stop,map or retry call is added;short input skips the block and follows the existing refusal path. Types and class layout remain unchanged.

Only scalar byte-count predicates run on the host. All75 nonzero short counts refuse the new clause;exact0x4c,larger andSIZE_MAX controls preserve the old decision. They do not model a window,base,address,provider or successful getter. Three source corruptions reject loss of the gate,an insufficient last-read bound and an added read. Sanitizers and one new real-header iOS17 Service candidate object pass;the object is never linked or executed. Original catalog,pins,32 patches,8 profiles and other Service candidates remain unchanged/uncombined. This does not close object/map/quiescence/stop/SMMU ownership requirements.

Previous Ring/VM scalar-capture candidates explicitly did not recover this underlying native channel. Review their scopes before a new first-failure capture candidate;never invent the raw value or execute a cache/provider callback to test it.
