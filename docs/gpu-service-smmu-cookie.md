# Persistent SMMU callback-cookie storage

The exact Service source builds an automatic NativeAdrenoSmmuWindow in start(), then puts its address in a local ArmSmmu4KIo passed to the persistent gmu_ctx_.bringUp. The exact context passes that I/O descriptor to smmu_.program and vm_.attach. Both persistent consumers copy the I/O record by value, retaining its cookie pointer; later observer/TLB paths read io_.cookie. A copied I/O record does not deep-copy the automatic window. Context failures after a successful program or after VM attachment can retain that cookie too. This is a source lifetime defect, not an observed native fault.

The prior GPU/CP cookie patches cover other descriptors and do not repair this SMMU window. The separate copied-SMMU-service-reference repair likewise changes object-reference duration, not cookie storage. An independent UNAPPLIED candidate moves the exact POD type before the Service declaration, adds a zero-initialized private smmu_window_ member, and initializes the same supplied base/bytes there before passing its address. The local ArmSmmu4KIo remains local because consumers copy its value. No callback, mapping, cache, route, stop or allocation behavior changes.

Four source corruptions reject restoration of automatic storage, a null cookie, deletion of the member and initialization after borrowing. Reversing the exact storage edits reconstructs the entire original source. No successful provider, native context, pointer/address peer or MMIO operation was modeled or executed.

One changed-candidate nonoptional iOS17 Service object compiled with actual existing target headers. Its real private class layout grows from the historical 3192 bytes to 3208, with the new 16-byte window at offset 3192. This is independent of the previous CP candidate even where their total byte sizes happen to match. Any eventual integration needs consistent Service storage/whole-owner rebuilding; this object is not a final kernel or Apple ABI qualification. The existing metaclass initializer remains unexecuted. No generated board/CommandDB/vote policies or frozen role APIs were supplied.

Persistent cookie storage does not retain the service object, mappings or powered hardware; it does not prove quiescence or authorize SMMU access. Original catalog sources, the 32 old patches and 8 profiles remain unchanged, with all candidates separate and unselected. No old suite, fullcore, service, bringUp, VM/cache/native callback or device operation ran.
